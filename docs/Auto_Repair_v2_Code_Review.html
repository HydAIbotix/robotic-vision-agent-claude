CODE REVIEW · AUTO-REPAIR AGENT

Auto-Repair v2 — Fixing the right code

Why our self-healing agent couldn't fix a simple bug — and the redesign that fixes it for every test
Kiosk-QA platform · Auto-Repair pipeline · Prepared for team code review · 20 Sep 2026

This is a plain-language walkthrough of a real Auto-Repair failure, what actually caused it, and the four changes we made. The headline: it was not a weak-model problem. Our agent was handing the model the wrong code, so no model could ever fix the bug. We fixed the targeting.

1. What went wrong (the real story)

Auto-Repair runs after a test fails: it retrieves the likely-buggy code, asks an AI model to diagnose a one-line fix, applies it, builds, and opens a PR. On test TC-RPS-003 it produced a confident but useless fix, even with a strong 32-billion-parameter code model (Qwen) and Microsoft GraphRAG.

We turned on a new debug dump and it told the whole story:

  • The test is titled "Mock card payment with sufficient balance succeeds."
  • But it actually failed much earlier — at Add to Cart: the product was added with quantity 0, which popped a "Quantity Required" message, so the cart never filled.
  • The retrieval step pulled 16 chunks of code and documents — all about payment / card readers. The actual buggy Add-to-Cart code was in none of them.
  • So the model did the only thing it could with what it was given: it tweaked the payment approval logic. Reasonable guess, wrong bug.
The one-sentence root cause: retrieval anchored on the test's title/goal (payment) instead of on where the test actually broke (add-to-cart). A model can only fix code it can see — and the buggy code was never retrieved.

2. Why it happened — three causes

1. The query described the goal, not the failure. The text we search with leads with the test's design intent ("payment… balance… approved"). For a test that dies early, those words point retrieval at the wrong feature.

2. Too much noise. 16 chunks were sent — half of them generic requirements prose and unrelated dummy settings. That dilutes the few lines that matter and confuses the model.

3. No sanity check on the answer. The wrong fix was type-valid, so it sailed through — nothing asked "does this patch even touch the thing that failed?"

3. What we changed — four fixes

The fixes are generic — they key off how any test fails, not off this one bug — so they help every customer and every failure type.

P0a  Aim retrieval at the failure point

We now build the primary search query from where the test actually broke — the failed step, the observed symptom, and the failing assertion ("Add to Cart… quantity 0… Quantity Required popup… expected cart, got products"). We still also search by the executed steps and the original goal, and blend all the results, so value-based bugs (e.g. a shared card balance that didn't update) still find their code. For TC-RPS-003 this pulls the add-to-cart code instead of payment code.

P1  Send fewer, sharper chunks

We sort failures into two kinds. A value / spec bug (balance, transaction, cross-kiosk) keeps the richer context and the design document — unchanged, so nothing that works today breaks. A plain interaction bug (wrong screen, popup, a button that did nothing) gets a tight, code-heavy set (~8 chunks, almost all code, boilerplate dropped). That removes the noise that misled the model.

P0b  Check the fix is on-target

After the model proposes a patch, we ask a simple question: does this patch touch the same things that failed? If the patch shares nothing with the failure symptom and a better-matching piece of code was right there in the context, we treat it as off-target and give the model one nudge back toward the symptom — keeping whichever answer is better, never getting stuck. (If nothing relevant was retrieved at all, we log that clearly: it's a retrieval gap, not a model mistake.)

P2  Optional "locate first" pass (RCA)

Optionally, a quick first step asks the model to name the suspect area and keywords before we search for the fix, which sharpens retrieval further. It's off by default (it adds a model call, slow on the local 32B) and can be switched on once the anchored retrieval is proven.

Each layer is conservative: if it has nothing useful to add, it does nothing and the flow behaves as before. That's how we keep the changes safe.

5. Screenshots & vision — an important limitation

Screenshot / image analysis can only be done by Claude or another multimodal model. Our local code model (qwen2.5-coder) is text-only — it cannot read images, so we do not send screenshots into the local code-fix path. If we want the agent to look at the failure screen (e.g. to read an on-screen error or see which control is highlighted), that step must run on Claude (or a multimodal model). The text signals we already capture — the failed step, the observed symptom, and the DOM assertion — are what drive the new retrieval today, and they are enough to fix this class of bug.

6. Is it safe? (no regressions)

  • Same pipeline shape. The changes live inside the existing retrieve → diagnose → apply → build → PR steps — no new agent, no re-wiring.
  • Value/spec bugs unchanged. The richer path (design doc + generous context) is byte-for-byte the same, so the working cross-kiosk demo does not regress. Only interaction bugs get the new tight profile.
  • Additive & reversible. Every new behaviour is behind a setting and is a no-op when it has nothing to contribute. Turn any of them off to get the old behaviour.
  • Tested. 8 new unit tests reproduce the exact live failure and prove the fix. Full suite: 128 passed; the only failures are 8 pre-existing ones (missing local screenshot fixtures / no API key) that fail the same way without our changes.

7. What's next (roadmap)

  • Re-run the failed test as the real oracle. The strongest possible check is to re-run the failing test against the patched app and confirm it now passes. We've built the on-target check as a fast stand-in; the full re-run is deferred only because it needs the patched POS redeployed (an operational coupling we didn't want to add in a no-regression change).
  • Richer execution logs. Feed a structured trace of the run (screen transitions + the action and its arguments at the failure) into the context for even sharper targeting.
  • Vision step on Claude. An optional "look at the failure screenshot" step, on Claude/multimodal, for bugs that are only visible on screen.
